# 关于 Special Spawner 刷新计时疑问的回复

回复日期：2026-09-15  
核对版本：`specialspawner_fullslots 1.3.11-night`

## 一、结论

疑问文档对当前代码执行顺序、8人生还者示例和刷新时间的计算均理解正确。

当前插件确实会：

```text
统计本批生成前的存活特感数
→ 生成本批特感
→ 仍按生成前的数量安排下一轮正常刷新
```

因此，8人生还者、场上0只特感时，按当前配置会先尝试生成9只，然后仍按0只特感对应的3秒间隔安排下一轮；如果这9只仍然存活，3秒后会再尝试生成剩余的5只，使场上数量接近14只上限。

但这段行为不能仅凭现象直接判定为后来修改产生的BUG。对原版 `Special Spawner 1.3.7` 源码进行核对后，可以确认原版同样使用生成前的 `totalSI` 安排下一轮计时。`1.3.11-night` 在处理满槽、Kick Queue 和部分生成失败时保留了这段原版计时算法，并未新引入这一行为。

## 二、代码事实与设计意图需要分开

### 已经能够确认的代码事实

1. 下一轮正常刷新时间使用生成前的特感数量。
2. 本批实际成功生成多少只，不会重新修正已经准备设置的正常刷新时间。
3. 1秒缺额 Retry 不会重新启动或延后正常刷新计时器。
4. 下一次正常计时器触发时，会重新统计场上实际存活特感，因此仍受总上限限制。
5. 当前 Retry 最多执行一次，不会产生无限 Retry Timer。

### 无法只靠源码完全确认的事项

无法替原作者直接确认这段代码究竟是有意设计，还是早期实现中遗留的计时偏差。源码只能证明它从原版 `1.3.7` 起就是这样运行的。

不过，根据 `ss_time_mode 1` 的说明“杀得越快刷得越快”，生成前的剩余特感数量可以被理解为对上一阶段清怪效率的采样：

```text
计时器触发时剩余较少
→ 说明上一批清理较快
→ 下一轮等待较短

计时器触发时剩余较多
→ 说明场上压力尚未解除
→ 下一轮等待较长
```

从这个角度看，当前算法更接近“根据队伍清怪速度主动施压”，不只是简单地根据当前总数量进行节流，因此存在成为原设计意图的可能。

## 三、对疑问文档五个问题的回答

### 1. 应该根据生成前还是生成后计算？

当前实现明确根据生成前计算，原版 `1.3.7` 也是如此。

若问哪一种更合理，则取决于期望的玩法：

- 生成前计算：队伍清得越快，后续批次来得越快，压力更主动。
- 生成后计算：场上特感越多，下一批等待越久，节奏更平缓。

### 2. 当前目标是否是尽快填满上限？

从实际效果看，是的。尤其当计时器触发时场上接近0只特感，插件会使用最低间隔安排下一轮，因此可能通过连续两批较快接近动态上限。

### 3. 部分生成成功是否影响正常计时？

目前不会。

例如计划生成9只但首次只成功3只，正常刷新时间仍根据生成前数量确定。缺少的6只可能在1秒后通过 Retry 再尝试，但正常计时器不会因此重新计时。

### 4. 1秒 Retry 是否影响下一轮正常刷新？

不会直接影响。

Retry 是当前批次的缺额修复，不会创建第二条正常刷新循环，也不会重置已经安排好的正常计时器。不过，Retry 生成出的特感会在下一次正常计时器触发时被统计，所以插件不会无视它们继续突破总上限。

以当前 `ss_time_min 3.0` 为例，可能出现：

```text
0秒：正常批次首次生成
1秒：Retry 尝试补齐本批缺额
3秒：下一轮正常计时器触发并重新统计场上数量
```

### 5. “杀得越快刷得越快”是否应忽略刚生成的特感？

当前算法会忽略本批刚生成的特感，以便延续根据上一阶段清怪结果施压的逻辑。

如果改为生成后统计，它表达的含义就会变成“当前场上数量越多，下一轮越慢”。而且计时器设置完成后，玩家即使立刻击杀本批特感，也不会自动缩短已经确定的等待时间。除非额外监听死亡并重排计时器，否则生成后统计并不能完整实现“杀得越快刷得越快”。

## 四、疑问文档中候选修正的实际影响

候选方案在生成后再次调用 `GetTotalSI()`，确实能让下一轮时间反映首次生成后的数量。

以8人生还者为例：

```text
当前算法：生成9只后，约3秒再尝试下一批
候选算法：生成9只后，约9.92秒再尝试下一批
```

这不是很小的修正，而是明显改变服务器压力模型。

此外，该候选代码在存在1秒 Retry 时仍有一个边界：生成后的第二次统计发生在 Retry 之前，因此不会包含稍后由 Retry 补出的特感。若目标是严格按本批最终实际数量计时，还需要决定是否等待 Retry 完成后再启动下一轮正常计时器。这会增加正常计时器与 Retry 之间的状态协调，不能只增加一次 `GetTotalSI()` 就算完全解决。

直接再次调用 `GetTotalSI()` 还会重复执行其中的死亡 Bot 清理副作用。若以后采用生成后计时，更稳妥的实现是让 `ExecuteSpawnQueue()` 返回本次实际成功生成数量，再根据生成前数量与成功数量计算，而不是单纯重复扫描全部客户端。

## 五、可选方向

### 方案A：保持原版算法

适合希望实现：

```text
队伍清怪越快
→ 插件越快继续施压
→ 较快填充动态特感上限
```

优点是保持原版行为和现有平衡；缺点是高人数、大批量、低 `ss_time_min` 时容易形成短时间连续灌特。

### 方案B：完全改为生成后数量计时

适合希望实现：

```text
每批生成后根据当前真实占场数量
→ 决定下一轮等待时间
```

优点是节奏平缓、每批特感拥有更长行动时间；缺点是会明显降低连续压力，而且对玩家在等待期间快速清怪的行为反应不及时。

若选择此方案，还需要明确 Retry 是否完成后重新计算正常计时。

### 方案C：保留原算法，但增加成功生成后的最低缓冲时间

这是目前更适合继续讨论的折中方案。

仍然根据生成前数量体现清怪速度，但只要本批成功生成了特感，下一轮实际等待时间不得低于一个独立缓冲值，例如5到6秒：

```text
原算法算出3秒
成功生成了一批特感
最低缓冲设为5秒
→ 下一轮使用5秒

原算法算出9秒
→ 仍使用9秒
```

这样主要压制“9只刚出现，3秒后又来5只”的过密批次，不会把所有中高数量档位的刷新时间一起大幅拉长，也继续保留“上一阶段杀得快，后续压力更快”的特点。

这一缓冲最好作为独立 CFG 参数，而不是直接写死，便于多人实测后调整或关闭。

## 六、建议的后续讨论顺序

建议先确认服务器真正想要哪种体验：

1. 队伍越强，插件越积极连续施压。
2. 每批特感之间保留比较稳定的交战时间。
3. 保留动态施压，但限制最低批次间隔。

在目标没有确定前，不建议直接把计时改成生成后统计，因为这会让8人示例中的下一轮间隔从3秒直接提高到约9.92秒，实际压力下降会非常明显。

当前更倾向方案C：保留原版以生成前数量衡量清怪速度的机制，再通过可配置的批次最低缓冲限制极端连续生成。最终数值应通过多人实战决定，而不是只依据源码推算。

## 七、最终判断

疑问文档准确找到了当前刷新节奏形成的原因，但更适合将其称为“原版计时策略是否适合当前高人数服务器”，而不是已经确认的程序BUG。

`1.3.11-night` 的满槽补试与部分缺额 Retry 修复了波次丢失问题；生成前计时则是从原版继承的另一项玩法策略。两者会叠加形成更稳定且更集中的压力，但应分别评价，避免把原版计时策略误认为 Retry 修复意外引入的错误。
